# OBB の PC・スマホ同期 設計

2026-11-07 時点の案。実装の進み具合は「段階」の表のとおり。

## 概要

PC 版とスマホ版の間で、閲覧履歴・お気に入り・自分の書き込み履歴などを同期する。同期するのはテキストデータだけ。データは端末で E2E 暗号化し、サーバーには暗号文だけを置く。マージはすべて端末で行う。

- 対象は PC 版(Tauri)とスマホ版(Android の Kotlin)。Web(hono-bbs)は含めない
- 掲示板側の協力なしに、専ブラ同士だけで完結させる
- アカウントは作らない。使い始めに人の確認を 1 度通す。2 台目以降は鍵と許可証を受け取って参加する
- 何を同期するかは利用者が選ぶ
- 通信は HTTP だけのイベント駆動。WebSocket の常時接続や短い間隔のポーリングは使わない

## 置き場所

モノレポの `bbs-browser` に置く。共通テストとコネクタの正規化とログの移行が、すでにここにあるため。

| 場所 | 中身 |
| --- | --- |
| `apps/sync-server` | Cloudflare Workers + Durable Objects のサーバー。暗号処理を持たない |
| `packages/sync` | PC 版の暗号・マージ・同期(TypeScript) |
| `apps/android/.../sync` | スマホ版の同じ処理(Kotlin) |
| `packages/conformance/sync-*.json` | PC とスマホが同じ結果を返すための共通テスト |
| `packages/logstore`・`LogDb` | 送信待ちキューと同期の状態の表 |

## 脅威モデル

サーバーが丸ごと漏れても、履歴の中身・見ているスレ・書き込み権限が渡らない。

| 脅威 | 対策 |
| --- | --- |
| サーバーの DB 漏えい | 中身は暗号文。レコード ID は HMAC。認証トークンはハッシュのみ |
| 他人の同期領域へのアクセス | 256bit の認証トークン |
| 暗号文の入れ替え | AEAD の AAD にレコード ID を含める |
| 古い暗号文の再送 | ペイロードの HLC で古いものがマージに負ける |
| 大量の領域作成・データ送信 | 作成の許可証(Turnstile)、PoW、クォータ、放置削除 |
| 端末の紛失 | 鍵のローテーション。ただし端末に残るデータと権限系の値は漏れたものとして扱う |

### 守らないもの

- サーバーが更新を隠すこと。古い状態を見せ続けられても、端末は検知できない
- メタデータ。通信の時刻と量、IP、暗号文の長さ、レコードの数、どのレコードが何度更新されたか、削除の事実
- 端末が持つ平文のログ。OS とアプリの権限に任せる

暗号文の長さから中身を推測されにくくするため、平文は 256 バイト単位に埋めてから暗号化する。

## 同期するもの

テキストだけを同期する。画像の本体とサムネイルは同期しない。

| レベル | データ | 既定 |
| --- | --- | --- |
| 履歴系 | 閲覧履歴(スレタイ・板名・最終閲覧時刻)・既読位置 | オン |
| 履歴系 | お気に入りのスレ・板(並び順を含む)・サイトの登録 | オン |
| 履歴系 | 自分の書き込み履歴(板・スレ・スレタイ・レス番号・本文・時刻) | オン |
| 履歴系 | 上げた画像の履歴(URL・ファイル名・日時) | オン |
| 履歴系 | NG | オン |
| 履歴系 | 許可リストにある設定 | オン |
| 権限系 | 画像の削除キー・管理トークン | オフ |

次は同期しない。

- Cookie・セッション。端末ごとに書き込みの ID が変わることを画面で説明する
- パスワード・API キー・`postDeleteKey`・トリップ入りの名前
- 手元のログ(dat)・読んでいた画面の位置・タブの状態

設定は許可リスト方式にする。新しい項目は既定で同期しない。PC とスマホで持ち方が違う項目(文字の大きさなど)は、対応表にあるものだけを同期する。

## 手元の整理と削除

| 操作 | 同期 |
| --- | --- |
| 履歴から外す・お気に入りを外す | tombstone を送る |
| ログの削除 | 既読のリセットを送る。他の端末は未読に戻る。ログと履歴と書き込み履歴は消さない |
| 自動整理 | 同期しない |
| クォータ超過で古い履歴をサーバーから外す | tombstone を送るが、手元の履歴は消さない |

## 鍵

最初の端末で 256bit のマスター鍵 `K` を作り、HKDF-SHA256 で用途別の鍵を導出する。`K` はサーバーへ送らない。

| 導出鍵 | info | 用途 |
| --- | --- | --- |
| `auth_token` | `obb-sync/auth` | API の認証 |
| `k_data` | `obb-sync/data` | 履歴系の暗号化 |
| `k_secret` | `obb-sync/secret` | 権限系の暗号化 |
| `k_id` | `obb-sync/record-id` | レコード ID の HMAC |

HKDF の salt は空、長さは 32 バイト。`auth_token` は Bearer では小文字の 16 進で送る。

`space_id = SHA-256(auth_token)` とする(32 バイトそのもののハッシュの小文字の 16 進)。Worker はトークンから `space_id` を計算して Durable Object を選ぶので、トークンのハッシュを別に保存しなくてよい。

`k_secret` は暗号の用途を分けるだけで、端末を分ける効果はない。`K` を持つ端末は権限系も読める。

### 保管

- `K` は OS の鍵保管(Windows の資格情報・Linux の Secret Service・Android Keystore で包む)に置く。使ったことのない人の鍵保管は開かない
- Linux で Secret Service が使えないときは同期を始めず、理由を出す
- `K` と派生鍵は設定の書き出しとバックアップに入れない。どちらも許可リストにないことをテストで確かめる
- 全端末で失うと戻せない。任意でリカバリーコードを書き出せる

### 端末の追加

1. 既存の端末で「端末を追加」を押すと、`K` と許可証とサーバーの URL を含む QR と、同じ内容のコピー用コードを出す。中身は `obb1.<K の Base64URL>.<URL の Base64URL>.<許可証>`(`packages/conformance/sync-pairing.json`)。新しい端末は Turnstile を通さない
2. スマホは QR を読む。PC にはカメラがないので、コピー用コードを入れる
3. 60 秒で消す。表示中は警告を出し、スマホでは画面の撮影を止める
4. 任意の 6 桁 PIN で、中身を Argon2id の鍵で暗号化できる。写真を撮られたあとの総当たりには強くないので、補助として扱う

### 暗号

- AEAD は XChaCha20-Poly1305。ノンスは毎回ランダム
- ノンスは暗号の処理の中で作り、外から渡す口を作らない。テストは固定のノンスで作った暗号文を開く向きで確かめる
- AAD は `space_id|record_id|kind_tag|schema_version` の UTF-8(区切りは `|`、前後に空白なし)。`space_id` と `record_id` は 64 桁の小文字の 16 進、`kind_tag` は `h` か `s`、`schema_version` は 0 以上の整数の 10 進で、ほかは拒否する。サーバーが振る `version` は暗号化の時点で分からないので入れない
- 埋め草は ISO/IEC 7816-4(`0x80` の後を 0 で埋める)で、次の 256 バイトの倍数まで。必ず 1 バイト以上増える。暗号文は埋め草の長さ + タグ 16 バイトで 16KB まで
- `nonce` と `ciphertext` は JSON では Base64URL(`=` なし)
- 例外の文は決まった符号だけにして、鍵と平文を入れない
- PC は `@noble/ciphers` と `@noble/hashes`
- スマホは BouncyCastle(`bcprov-jdk18on`)。XChaCha がないので HChaCha20 だけ足し、ChaCha20-Poly1305・HKDF・HMAC はライブラリのものを使う。JVM の単体テストで端末と同じコードが動き、純 Java でネイティブのライブラリが増えない。Argon2 もある
- 両者の一致は共通テスト `sync-crypto.json` で確かめる

### 鍵のローテーション

1. 残った端末で `K'` を作る
2. 全レコードを再暗号化し、新しい領域へ送る
3. 古い領域を消す
4. 他の端末は 401 を受けて、再ペアリングを案内する

権限系の値はローテーションでは守れない。画面で、画像の削除キーは漏れたものと考えるよう案内する。

## データモデル

### レコードの ID

```
record_id = HMAC(k_id, "<種類>:<正規化した板 URL>:<スレ>[:<細目>]")
```

`record_id` は小文字の 16 進。各項目の `%` と `:` は `%25`・`%3A` に逃がす(細目に URL が入っても別のレコードと同じ ID にならない)。板のないレコード(設定など)は板を空にする。

板 URL の正規化は `sync-id.json` で PC とスマホを揃える。`5ch.net` と `5ch.io`、http と https、道のある板、末尾の `/`、大文字のホストを同じ規則にする。板名だけでは、別のサイトの同じ名前の板がぶつかる。形はスキームを除いた `ホスト[:ポート]/道/`。http・https 以外は拒否する。

スマホ版にない掲示板(ふたばなど)のレコードも、捨てずに持ち続けて再送する。

### サーバーのレコード

サーバーはレコードごとに最新の 1 件だけを持つ。

```
{
  record_id,
  version,            // 領域の中で単調増加。サーバーが振る
  kind_tag,           // "h" | "s"
  schema_version,
  deleted,            // tombstone か。平文。サーバーの片づけに使う
  nonce, ciphertext,
  updated_at          // サーバーの受信時刻
}
```

`deleted` が平文なのは、中身の見えないサーバーが tombstone を片づけるため。削除の事実はサーバーに見える。端末は平文の `deleted` を見ず、暗号文の中の値を使う(AAD に入っていないので、サーバーが変えられる)。

### ペイロード

暗号化する中身は次の形。知らないフィールドは捨てずに保持する。

```
{ kind, hlc, device_id, deleted?, body?, ...知らないフィールド }
```

- `kind` は種類。`record_id` は片道の HMAC なので、受け取った端末は中身を見ないと種類が分からない
- tombstone は `body` を残さない(最終閲覧時刻だけは max のために残す)
- 数は安全な整数だけ。小数の書き方は言語で違い、キーを並べた JSON が PC とスマホで変わる。順序キーのような小数は文字列で持つ
- 開くときの決まり: 壊れたレコードはそれだけ捨てて理由ごとに数え、ほかを止めない。JSON は深さ 32 まで。復号後の値は種類ごとの決まりで型と長さを検査する。知らない種類は決まりの外なので通して持ち続ける。種類ごとのフィールド名と上限は `docs/sync-client.md` の 4 章で実際のデータに合わせて見直す

### マージ

すべてのマージ関数を可換・結合的・冪等にする。

| 種類 | 単位 | 書く端末 | 規則 |
| --- | --- | --- | --- |
| 既読 | スレ×端末、スレごとのリセット | 下記 | 下記 |
| 最終閲覧時刻 | スレ | 全端末 | 時刻は max、ほかは LWW。tombstone をまたいでも max(時刻を除いて勝ち負けを決める。除かないと結合的でなくなる) |
| お気に入り | スレ・板 | 全端末 | LWW。削除は tombstone |
| 並び順 | お気に入りごとの小数の順序キー | 全端末 | LWW。同じ値は ID で並べる。キーは `0.` の後の桁の文字列で、末尾は 0 にしない。文字列の比較がそのまま大小になり、桁が尽きない |
| 自分の書き込み | 板・スレ・時刻・本文から決める `post_id` | 全端末 | LWW。レス番号が返らない掲示板があるので番号を ID にしない |
| サイトの登録 | メニューの URL | 全端末 | LWW。削除は tombstone |
| 上げた画像の履歴 | URL | 全端末 | LWW |
| NG・設定 | 要素 | 全端末 | LWW。NG の正規表現は `ng.json` の決まりに従う |
| 削除キー | 画像 | 全端末 | LWW(`k_secret`) |

### HLC

- 形は `壁時計(ms)12 桁の 16 進.カウンター 4 桁の 16 進.device_id` の文字列で、文字列の比較がそのまま順序になる。`device_id` は `[A-Za-z0-9_-]` の 64 文字まで
- `device_id` は鍵保管と DB の両方に持ち、起動時に比べる。別の端末の DB を入れて違えば、同期の表を消して新しい `device_id` で合流し直す(`docs/sync-client.md` の 8 章)
- 同じ値は `device_id` の辞書順で後の方を勝ちにする。端末を戻すなどで HLC も端末も同じになったら、キーを並べた JSON の順で決める(どの順で受け取っても同じ結果にする)
- 端末に保存する
- 受け取った HLC が今の時刻より 24 時間以上先なら、そのレコードには適用するが、端末の HLC は進めない
- レコードを更新するときは、必ずそのレコードの HLC より大きくする。時計の狂った端末が書いた値も、次の更新で上書きできる。その値が 24 時間以上先なら、更新の値だけが先へ進み、端末の HLC は進めない

時計のずれた端末の書き込みが、実際の順序と逆に勝つことはある。LWW の制約として受け入れる。

### 既読

既読位置を max にすると未読に戻せず、LWW にすると古い端末の位置へ巻き戻る。そのため端末ごとの記録とリセットに分ける。

```
// スレごと・全端末が書く(LWW)
reset: { id, at: HLC, target_res }

// スレ×端末ごと・持ち主だけが書く
dev: {
  base_reset_id,            // この端末が知っている最新のリセット
  pos,                      // base_reset 以降に読んだ最大のレス番号
  steps: [{ at: HLC, pos }] // まだ知らないリセットに備えた記録
}
```

`reset.at` はペイロードの `hlc`、`id` と `target_res` は `body` に置く。`dev` も `body` に置き、記録全体はペイロードの `hlc` で LWW にする。

`steps` は、読むたびに `{ 今の HLC, 読んだ位置 }` を足し、後ろの要素以下の `pos` の前の要素を消す。これで `at` が進むほど `pos` が小さくなる並びになり、任意の時刻より後の最大の位置を先頭側から求められる。最新の 8 件までを持つ。8 件を超えて捨てた分は、知らないリセットの後の読みとして数えられないことがある(既読位置が低く出るだけで、端末間では一致する。テストで確かめた)。

既読位置の計算は次のとおり。

1. `R` = 最新のリセット(なければ id=null・at=0・target_res=0)
2. 各端末の記録について、`base_reset_id` が `R.id` と同じなら `pos` を候補にする
3. 違うなら、`steps` のうち `at > R.at` の `pos` の最大を候補にする
4. 既読位置 = max(`R.target_res`, 候補)

読んだとき、自分の `base_reset_id` が最新のリセットと同じなら `pos` を増やす。違えば `base_reset_id` を更新し、`pos` は「読んだ位置と、そのリセットより後の `steps` の最大」にする。どちらの場合も、そのリセット以前の `steps` を消してから今の読みを足す。

- 前の読みを引き継ぐのは、知らないうちに読んだ分が、同期のあとの読み直しで消えて既読位置が下がらないように
- 今の読みを必ず足すのは、まだ知らない別のリセットより後の読みかもしれないから

ログを削除するときは新しい `reset` を書く(未読に戻す操作を兼ねる)。その HLC は、今のリセットと、知っている全端末の記録と `steps` より必ず大きくする。時計が先へ進んだ端末の読みが残っていると、未読に戻せないため。

| シナリオ | 結果 |
| --- | --- |
| PC で 500、スマホで 300 まで読んだ | 500 |
| PC で 500 まで読んだ後、スマホで未読に戻した | 0 |
| スマホで未読に戻した後、知らないオフラインの PC で 350 まで読み、次に開いて 100 まで読んだ | 350 |
| PC で 500 まで読み、スマホで未読に戻した後、PC が同期した | 0 |
| 2 台で同時に別の位置へ未読に戻した | HLC が新しい方 |
| スマホで未読に戻した後、PC が 350 まで読み、同期してから 100 まで読んだ | 350 |
| 時計が 3 日先の PC が 500 まで読み、それを見たスマホで未読に戻した | 0 |

### tombstone と長期オフライン

- サーバーは `deleted` のレコードを 90 日後に消し、消した最大の version を `gc_floor` として返す
- `since < gc_floor` の端末は全件を取り直す(リベース)
- リベースでは、同期済みなのに全件の中にないものを手元から消す。削除済みが手元に残って端末間でずれないため。全件を最後まで受け取れなかったときは消さない
- 未送信の変更のうち、HLC が 90 日より古いものは捨てる。そのレコードの手元の値も未送信を含むので、全件の値に戻すか、全件になければ消す
- 一度も同期していないもの(`version` が 0。クォータでサーバーから外した手元だけの履歴を含む)は消さない
- 手元の値が全件の値に勝つとき(サーバーが古い値に戻ったときなど)は、送信待ちに入れる
- 消えるもの(tombstone の片づけは数えない)が、全件が空のとき、または 10 件以上かつ同期済みの 20% 以上のときは、自動で消さずに確認を出す。リベースの関数は適用せず、計画を返す
- 同期領域には `epoch` を持たせ、全応答で返す。変わっていたら領域が作り直されたので、手元を消さずに全件を合わせ直す(次節)

### 領域が消えたとき

**サーバーは保管庫ではなく、端末の間の中継の置き場。** データの正は各端末の手元にある。領域は押し出し・放置削除・管理者の削除・サーバーの事故で消えることがある。どれも同じ流れで戻る。

1. 404 を受けた端末は、確認なしで、保管している許可証を付けて同じ鍵の領域を作り直す
2. 全件を取り直し(空か途中まで)、手元の全レコードとマージして、違うものを全部送る
3. ほかの端末は 404 か `epoch` の変更で気づき、同じくマージして送る。手元は消さない
4. マージは可換・結合的・冪等なので、どの順でも全端末が同じ状態に収束する

- 端末は tombstone を、その端末で tombstone になってから 90 日残す。サーバーの領域が消えても残すので、削除済みが復活しない
- 90 日以上オフラインだった端末は、期限の切れた tombstone を知らないので、削除済みの項目を復活させることがある。LWW の制約として受け入れる
- 満員なら作り直せない。手元は残り、次に開いたときにまた試す
- 許可証の期限切れ・鍵の交代で断られたときは、待っても直らないので止まる。手元は残り、利用者が確認を通し直すと続く
- リベースで手元が大量に消えるときの確認は残す。作り直しは手元を消さないので確認が要らない

## API

| メソッド・パス | 認証 | 内容 |
| --- | --- | --- |
| `GET /start?space_id=…&return=app` | なし | 同期を始めるページ(Turnstile) |
| `POST /tickets` | Turnstile のトークン | 許可証の発行。本文 `{ turnstile, space_id }`、応答 `{ ticket, exp }` |
| `POST /spaces` | トークンと許可証 | 領域の作成。本文 `{ ticket, pow? }` |
| `GET /changes?since=N` | トークン | version N より後の変更(最大 500 件・1MB) |
| `POST /records` | トークン | 一括送信(最大 100 件・1MB) |
| `GET /head` | トークン | 最新の version と `epoch`。ETag と 304 |
| `GET /space` | トークン | 使用量・クォータ |
| `DELETE /space` | トークン | 領域の削除 |

認証は `Authorization: Bearer <auth_token>`。

### 同期の手順

1. `GET /changes` で差分を取り、復号してマージする
2. 送信待ちを暗号化し、`POST /records` で送る。各レコードに `base_version` を付ける
3. `base_version` は、端末が最後に見たその**レコードの** version。新しいレコードは 0
4. サーバーのそのレコードの version が `base_version` より新しければ、その 1 件は 409 になり、応答に今のレコードが入る。端末はマージして再送する
5. 成功したら、新しい version を保存する

### タイミング

**同期はアプリが前面にいる間だけ行う。** PC もスマホも同じ規則で、バックグラウンドの処理を持たない。

| pull のきっかけ | 検知 |
| --- | --- |
| スマホでアプリを開く・復帰する | 前面復帰 |
| PC でウィンドウに戻る | focus・visibilitychange |
| PC で放置後に操作する | 最終操作から 10 分以上空いた最初の操作 |
| ネットワークの復帰 | 接続が戻って 5 秒待ち、前回の同期から 30 秒以上空いていれば同期する |
| 保険 | 前面にいる間だけ 5 分に 1 回 `GET /head` |

pull は前回から 10 秒以上空ける。

push は次のとおり。

- 変更は送信待ちに溜め、同じレコードは最新の 1 件にまとめる
- 既読はスレを閉じたときに 1 回だけ記録する
- 使用中は、変更があるときだけ 2 分ごとに送る
- お気に入りや書き込みなどの重要な操作は 10 秒のデバウンスで早めに送る
- 裏に回る瞬間と窓を閉じるときに 1 回だけ試す。OS に止められてもよい。送信待ちは残り、次の前面復帰で送る

値は定数にする。**限界:** スマホで読んですぐ閉じ、送れなかった分は、次にスマホを開くまで他の端末に届かない。画面で説明する。

### エラー

- 1 秒から最大 60 秒の指数バックオフとジッターで再送する。409 はマージして再送し、それ以外の 4xx は再送しない
- 413(クォータ超過)は、古い閲覧履歴と既読から順にサーバーのものを外して再送する。お気に入り・NG・設定は外さない。それでも足りなければ画面で知らせる
- HTTP は 10 秒で打ち切る
- `request_id` で二重の採番を防ぐ
- 画面に「同期中」「同期済み」「送信待ち N 件」「オフライン」を出す

## サーバー

同期領域 1 つに Durable Object(SQLite)を 1 つ割り当てる。通番と楽観ロックは Durable Object の中で完結する。

- トークンから `space_id` を計算して呼ぶ。未作成の領域は空のまま 404 を返す
- 放置削除とレコードの片づけは、各 Durable Object の alarm で行う
- 全体のレート制限は Cloudflare の Rate Limiting で行い、概算でよい。領域の数と作成元の数は台帳で正確に数える。IP ごとの回数は環境変数ではなく wrangler の設定(`RL_IP`・`RL_WIDE`・`RL_AUTH`・`RL_CREATE`・`RL_ADMIN`)で変える
- ほかの上限と期間は環境変数。一覧は `apps/sync-server/src/config.ts`。非常スイッチは `CREATION_CLOSED`(新規作成の停止)と `READ_ONLY`(読み取りだけ。書き込みは 503)
- IP は `space_id` と結び付けて長期に保存しない

### 不正利用対策

アプリ証明は使わない。公開リポジトリのアプリでは強い保証にならず、Play 以外で配る APK は Play Integrity を通らないため。

公開は 3 段に分ける。

| 段 | 対象 | 作成の入口 | 必須のもの |
| --- | --- | --- | --- |
| 検証用 | 開発者だけ | `workers.dev`。許可証(Turnstile は公式のテスト用のキーから始める)、PoW、レート制限 | 単体・統合のテスト |
| 限定の試験 | 先着 100 領域 | 許可証(実際のウィジェットの Turnstile)、PoW、作成元ごとの制限、枠の上限 | `docs/sync-security.md` の限定の試験の前の条件 |
| 一般公開 | 誰でも | 限定の試験と同じ入口を本番のドメインで | `docs/sync-security.md` の公開の前の条件 |

| 段階 | 対策 |
| --- | --- |
| 作成 | IP ごとの制限(IPv6 は /64)、許可証(Turnstile)、数秒の PoW(環境変数 `POW_BITS` で弱められる)、作成元ごとの制限、枠の上限 |
| 作成後 | クォータ |
| 運用 | 新規作成だけを止めるスイッチ、管理 API |

**削除と締め出しは完全な防御ではない。** 確認を通した人は新しいトークンで領域を作り直せる。本当の防御は、許可証・枠の上限・PoW・作成元ごとの制限で攻撃の費用を上げ、被害の上限を決めること。

### 許可証

領域を作るには、領域の作成の許可証が要る。利用者が 1 度だけ人の確認(Turnstile)を通すと、その `space_id` にだけ使える許可証を受け取り、以後は人の操作なしで領域を作り直せる。

1. 端末が `K` を作り、`space_id` を計算する(`K` はサーバーへ送らない)
2. 利用者が「同期を始める」を押すと、端末の窓で `GET /start?space_id=<64 桁の 16 進>&return=app` を開く
3. ページが Turnstile を通し、`POST /tickets` にトークンと `space_id` を送る
4. サーバーが Turnstile を検証し、許可証を署名して返す。ページが端末へ渡す(下記)
5. 端末は許可証を `K` と一緒に鍵保管に置き、`POST /spaces` に付ける

| 決まり | 内容 | 理由 |
| --- | --- | --- |
| 形 | `v1.<space_id>.<期限(秒)>.<鍵 ID>.<署名>`。署名は `HMAC-SHA256(鍵, "obb-sync-ticket-v1:" + 署名より前)` の Base64URL | 発行も確認も同じサーバーなので、公開鍵の署名は要らない |
| 鍵ではない | `K` もトークンも含まない。`POST /spaces` はトークンも要るので、許可証だけでは何も作れず、読めない | `space_id` はトークンのハッシュで、元に戻せない |
| 領域に結び付く | 署名の中の `space_id` が、トークンから計算した値と違えば断る | 1 回の確認で 1 領域だけ。別の領域に使い回せない |
| 保存しない | サーバーは署名を確かめるだけ。発行の記録を持たない | 発行した許可証の表も、消えた領域の控えも要らない。領域の履歴と IP を残さない |
| 何度でも使える | 押し出し・放置削除・管理者の削除のあとも、同じ許可証で作り直せる。枠・押し出し・作成元の制限・PoW はそのまま効く | 確認なしの作り直し(「領域が消えたとき」)を保つため |
| 期限 | 環境変数 `TICKET_TTL_DAYS`、既定 365 日。使っても延びない | 長めにして作り直しで人を呼ばない。期限があるので、悪用された領域も 1 年で確認を求められる |
| 期限切れ | `403 ticket_expired`。端末は `blocked` になり、手元はそのまま。「同期を始める」をもう一度押すと続く | 領域があるうちは許可証を使わないので、期限切れで同期は止まらない。止まるのは作り直しのときだけ |
| 複製 | QR とコピー用のコードに入れる。2 台目は Turnstile が要らない | 同じ `space_id` なので同じ許可証が使える |

**署名の鍵:** 秘密 `TICKET_KEYS`(`{"鍵 ID":"32 バイト以上の Base64URL"}`)に複数持てる。新しい許可証は環境変数 `TICKET_KID` の鍵で署名し、確認は登録のある鍵すべてで行う。読めない鍵が 1 つでもあれば全部を捨て、作成と発行を 503 で止める。環境ごとに別の鍵にする(検証用の許可証を本番で使えないように)。

| 場面 | 手順 | 配った許可証 |
| --- | --- | --- |
| 普段の交代 | 新しい鍵を足す → `TICKET_KID` を変える。古い鍵は残す | 使える |
| 鍵の漏えい | 新しい鍵を足す → `TICKET_KID` を変える → 漏れた鍵を外す | 断られる。次の作り直しで `ticket_invalid` になり、利用者が確認を通し直す |

**同期を始めるページ:** Turnstile のウィジェットと短いスクリプトだけの静的なページ。問い合わせの値をページに書かない。外部のスクリプトは Turnstile だけで、インラインのスクリプトは CSP のハッシュで固定する。

### 許可証の受け渡し

ページは決まった URL `https://obb-sync.invalid/ticket?ticket=<許可証>` へ `location.replace` で移ろうとし、端末の窓がその移動を止めて許可証を受け取る。PC は `on_navigation`(`apps/desktop/src-tauri/src/web_upload.rs` の `FOUND` と同じ)、スマホは `WebViewClient.shouldOverrideUrlLoading`。

| 注意する所 | 決め方 |
| --- | --- |
| 別の先へ返させる | `return` は `app` だけ。URL を受け取らないので、罠のリンクで他人の確認の結果を受け取れない |
| URL に残る | 許可証は `POST /tickets` の応答で受け取る。`/start` の URL には入らない。入るのは止める移動の URL だけで、読み込みが始まらないので履歴に載らない。`replace` なので、止め損ねても戻る操作の先に残らない |
| Referer | 止める移動は要求にならないので Referer が出ない。ページは `Referrer-Policy: strict-origin` で、Turnstile へ渡るのは origin だけ。問い合わせの `space_id` は渡さない |
| 止め損ねた | `.invalid` は名前解決されない(RFC 6761)ので外へ出ない。プロキシがあっても https の経路で見えるのはホスト名まで。漏れてもトークンがなければ使えない |
| キャッシュ | ページも応答も `Cache-Control: no-store` |
| 窓の中の別の文書 | 端末は上の階層の移動だけを受け取り、自分の `space_id` に結び付いた形の許可証だけを置く(`ticketSpaceId`)。署名と期限はサーバーだけが確かめる(端末の時計を信用しない) |

ほかの方式を選ばない理由。

| 方式 | 選ばない理由 |
| --- | --- |
| Android の `addJavascriptInterface`、Tauri の IPC | 窓の中の全部の文書から呼べる。開いたページにアプリの命令を渡さない |
| 独自のスキーム(`obb://`) | スマホでは別のアプリが同じスキームを取れる。止め損ねると OS へ渡る |
| 通常のブラウザで開いて戻す | 戻す道に独自のスキームか App Links が要る。PC に共通の方法がない |
| 手でコピーして貼る | どの環境でも動くが手間が大きい。窓で動かない環境が見つかったときの控えにする |

### 限定の試験の枠

- 枠は環境変数 `SPACE_LIMIT`(既定 100)。増やすときは環境変数を変える
- 招待の仕組みは作らない。匿名の掲示板で配れないため
- 枠が埋まったら押し出す(下記)。押し出せなければ `POST /spaces` だけを断る(403・`capacity_full`)。既存の領域の同期は止めない。403 なのは、端末の再送の決まり(4xx は再送しない)に合うから
- 作成の後に一度もレコードが来ない領域は、短い期限(環境変数 `EMPTY_SPACE_DAYS`、既定 7 日)で消す案
- 悪用で枠を埋められても、被害は 100 領域 × 10MB = 1GB で止まる。埋められたときは管理 API で消すか、環境変数で枠を増やす

### 押し出し

満員で新規作成が来たら、最終使用から一定期間(環境変数 `EVICT_IDLE_DAYS`、既定 14 日)空いた領域のうち、一番古いものを消して作る。

| 決まり | 内容 |
| --- | --- |
| 最終使用 | 認証を通った要求(`GET /head` を含む)。領域の Durable Object が日の変わり目に台帳へ報告する |
| 選び方 | 台帳で候補を選ぶ。**消す前に領域の Durable Object の本当の最終使用を確かめる**(報告の遅れや失敗で使用中の領域を消さないため)。新しければ台帳を直して次の候補へ |
| 該当なし | `capacity_full` |
| 競合 | 台帳の 1 つのトランザクションで候補を `deleting` にして枠を移す。同時の作成が同じ候補を選ばず、枠の数を超えない |
| 押し出された端末 | 次の同期で 404 を受け、確認なしで作り直す。手元は消さない |
| 消し合い | 作り直した領域は最終使用が今になるので、14 日は押し出されない。押し出せるのは 14 日空いた領域だけなので、使っている人どうしで消し合わない |
| 放置削除 | 押し出しとは別に残す(空きがあっても 90 日で消す) |

押し出された人の損失は、サーバーの中継のデータだけ。端末を全部失っていれば戻せない。これが「保管庫ではない」の意味で、画面で説明する。
- 端末は同意して使う試験機能で、手元のデータが正。同期を切っても、サーバーのデータが消えても、手元は消えない

### 台帳

Durable Object は列挙できないので、領域の一覧を持つ台帳を 1 つ持つ。**台帳用の Durable Object(SQLite)を選ぶ。**

| 比較 | 台帳用の Durable Object | D1 |
| --- | --- | --- |
| 枠の確認と作成の予約、nonce、監査、停止の印を 1 つのトランザクションで | できる。1 つの実体が順に処理する | 文ごとの工夫が要る |
| 使う製品 | 領域と同じ。Miniflare で同じように試せる | 1 つ増える |
| 一覧の集計 | SQL で足りる | SQL で足りる |
| 規模の限界 | 1 つの実体に要求が集まる | 伸ばしやすい |

試験と初期の公開の規模では台帳への要求が少ない(作成と、間引いた報告だけ。同期の通信は通らない)ので、規模の限界より一貫性を取る。伸びたら D1 へ移せるよう、台帳は内部の口(`Ledger`)の裏に置く。

| 項目 | 内容 | 更新 |
| --- | --- | --- |
| `space_id` | 領域 | 作成 |
| `created_at` | 作成の時刻 | 作成 |
| `last_access_day` | 最終アクセスの日 | 日が変わったとき |
| `used_bytes`・`record_count` | 使用量 | 10% 以上変わったとき。最大で 1 時間に 1 回 |
| `req_recent` | 直近 1 日の要求数 | 1 時間に 1 回 |
| `source_mac` | 作成元の値(下記)。7 日で消す | 作成 |
| `state` | `active`・`deleting` | 押し出し・削除 |

領域の Durable Object が台帳へ報告する。中身と鍵は台帳に入らない。

### 作成元

作成のときだけ、IP(IPv6 は /64)を週替わりの鍵で HMAC した値を台帳に置き、7 日で消す。

| 決まり | 内容 |
| --- | --- |
| 鍵 | 台帳の Durable Object の中でランダムに作る。環境変数から導かない。今週と先週の 2 つを持ち、それより古い鍵は捨てる |
| 保存しないもの | 平文の IP、User-Agent(CLI で偽れるので判断材料にしない) |
| 結び付けないもの | 同期の通信の IP と領域 |
| 使い道 | 作成元ごとの制限(環境変数、既定は 7 日に 5 領域)、管理者の判断材料、締め出し |

| 得失 | 内容 |
| --- | --- |
| 得るもの | IP を持たずに、同じ所からの作成の集中が分かる |
| 残るもの | 鍵が残っている間、DB を読める人は IPv4 の全部(2^32)を総当たりで戻せる。匿名ではなく仮名 |
| 限度 | 7 日で値が消え、14 日で鍵が消える。その後は戻せない。プライバシーの説明に書く |

### 管理 API

`/admin/v1/` の下に置く。別のドメインにはしない。詳しい安全性は `docs/sync-security.md`。

**認証:** Ed25519 の署名。公開鍵を環境変数 `ADMIN_KEYS`(鍵 ID → 公開鍵)に登録する。秘密鍵は管理者の手元だけ。

```
obb-sync-admin-v1
<METHOD>
<host>
<path>
<並べた query>
<本文の SHA-256 の 16 進>
<時刻(秒)>
<nonce>
<鍵 ID>
```

- ヘッダー `X-OBB-Admin` に鍵 ID・時刻・nonce・署名を入れる。形は `kid=<鍵 ID>,ts=<秒>,nonce=<Base64URL>,sig=<Base64URL>`。`ADMIN_KEYS` は `{"<鍵 ID>":"<公開鍵 32 バイトの Base64URL>"}` の JSON
- 並べた query は、生の `k=v` を文字列の順に並べて `&` でつなぐ(復号しない)
- 時刻は前後 60 秒。nonce は 16 バイト以上で、台帳に 5 分残して再利用を拒否する
- 失敗は普通の未定義のパスと同じ 404。レート制限を超えたときも 404。管理 API の存在を見せない
- host を署名に入れるのは、検証用への要求を本番で使い回せないようにするため

| メソッド・パス | 内容 |
| --- | --- |
| `GET /admin/v1/spaces` | 一覧(カーソル・並べ方) |
| `GET /admin/v1/spaces/{id}` | 1 件の詳細 |
| `DELETE /admin/v1/spaces/{id}` | 1 件の削除 |
| `POST /admin/v1/spaces/delete` | 複数の削除。本文に `ids`・`expected_count` |
| `POST /admin/v1/spaces/delete-all` | 全削除。本文に `expected_count`・`confirm`(本文ごと署名に入る) |
| `GET /admin/v1/jobs/{id}` | 削除の進み具合 |
| `GET /admin/v1/capacity` | 枠と使用数、新規作成の状態 |
| `POST /admin/v1/creation` | 新規作成の停止と再開 |
| `GET /admin/v1/signals` | 判断材料の集計 |
| `POST /admin/v1/sources/block` | 作成元の値を指定して、一定期間(既定 7 日)新規作成を断る |
| `DELETE /admin/v1/sources/block/{value}` | 締め出しの解除 |
| `GET /admin/v1/audit` | 監査ログ |

- 削除は台帳を `deleting` にしてから、領域の Durable Object の中身(ストレージと alarm)まで消す。途中で失敗しても台帳の alarm がやり直す
- 複数と全削除はジョブにして少しずつ進める。全削除は始めた時点の一覧だけを消し、その後に作られた領域に触らない
- `expected_count` が今の数と違えば 409 で何もしない。`confirm` は `DELETE ALL <件数> SPACES`
- 消された領域の再作成は断らない。攻撃者は新しいトークンを作れるので効果が薄く、誤って消された正規の人の復旧だけを妨げるため
- 締め出しは今週と先週の鍵で作成元の値を計算して比べる。鍵が捨てられると効かなくなるので、最長で鍵の寿命まで
- 自動では消さない。判断は管理者が行う
- 監査ログには、鍵 ID・操作・対象の数か ID・時刻を残す。管理者の IP は残さない
- 操作の道具は `apps/sync-server/scripts` の CLI。秘密鍵はリポジトリに入れない

判断材料(`signals`)は、作成元ごとの作成数、時間あたりの作成数、使用量と要求数の上位、作成後に使われない領域。

クォータの初期値は次のとおり。どれも環境変数で変えられるようにする。

| 項目 | 上限 |
| --- | --- |
| 領域の容量 | 10MB |
| レコード数 | 50,000 件 |
| 1 レコード | 16KB |
| 1 リクエスト | 100 件・1MB |
| 頻度 | 20 回/分・2,000 回/日・領域 |
| 放置削除 | 90 日 |

領域が消えた端末は、404 を受けたら確認なしで手元のデータから作り直す(「領域が消えたとき」)。Turnstile は使い始めの 1 度だけなので、作り直しと両立する(「許可証」)。

### 費用

1000 人が毎日、スマホを 3 時間、PC を 8 時間使うと仮定する。

| 項目(1 人 1 日) | 回数 |
| --- | --- |
| まとめ送信(スマホ 3 時間の上限) | 90 |
| 裏に回る・閉じるとき | 20 |
| 復帰・フォーカスの pull | 20 |
| PC の保険の確認 | 96 |
| スマホの保険の確認 | 36 |
| 合計 | 約 260 |

月に約 780 万リクエストになる。Workers と Durable Objects の込み分の内外、Durable Objects の実行時間、保存量は、実装の前に最新の料金表で計算し直す。全員が 10MB を使い切ると 10GB になる。テキストだけなので、実際はずっと小さいと見込む。

## 段階

端末の作業の詳細は `docs/sync-client.md`。

| 段階 | 内容 | 完了の目安 |
| --- | --- | --- |
| 0. 共通の核 | 鍵と暗号、マージ、HLC を TS と Kotlin で作る。`sync-crypto.json`・`sync-merge.json`・`sync-id.json`・`sync-schema.json`。プロパティテスト | 済み |
| 1. 縦の一本(偽サーバー) | 核のスキーマの直し。同期の表、拾い、アダプター、エンジン、偽サーバーを、**お気に入りのスレだけ**で全部通す。通信なし | PC とスマホの実装が偽サーバーで往復し、共通のシナリオが両方で通る |
| 2. サーバー | `apps/sync-server`。PoW、レート制限、クォータの枠、枠の上限と押し出し、台帳、作成元、管理 API と CLI、非常スイッチ。枠 2 の Miniflare の統合テスト | 済み |
| 3. 許可証 | `GET /start`・`POST /tickets`・`POST /spaces` の確認。エンジンが許可証を送る形(TS・Kotlin)。スマホのエンジンの PoW。Turnstile は公式のテスト用のキーで動かす | 否定のテストと共通のシナリオが通る |
| 4. 本物の 2 台 | **お気に入りのスレだけ**を本物の PC とスマホで同期する。スマホの PoW の実機の時間、本物の HTTP、鍵の保管、手動の同期、開発用の設定に隠したペアリング、許可証の受け渡しの窓。`workers.dev` に手動の `wrangler` で出す | 開発者の 2 台が実機で同期する。領域を消しても作り直して一致する |
| 5. 残りの種類 | 閲覧履歴・既読・お気に入り板と順序 → 書き込み履歴・上げた画像 → NG → 設定の許可リスト。初回の同期と 2 台目の合流。送信待ちとまとめ送り、きっかけごとの pull、再送、状態の表示、裏に回る瞬間の 1 回の送信 | 共通のシナリオの全部。1 万スレの偽データで初回の同期が画面を止めない。機内モードの復帰で追いつく |
| 6. 限定の試験 | 実際のウィジェットの Turnstile、試験機能の同意画面。枠 2 のシミュレーターにエンジンをつなぐ。検証環境で枠 2 にして PC とスマホのエミュレーターで通す手動のテスト | `docs/sync-security.md` の限定の試験の前の条件 |
| 7. 一般公開 | 本番のドメイン、利用規約など | `docs/sync-security.md` の公開の前の条件 |
| 8. 仕上げ | 権限系、ローテーション、リカバリーコード | 検証の全部 |

WebSocket は、同時利用のリアルタイム性が本当に必要になったときだけ検討する。その場合もデータは HTTP のままで、通知だけを送る。

## 検証

- 同じ変更をランダムな順序・重複ありで適用して、全端末が一致する
- 既読のシナリオ表のすべて
- お気に入りの追加と削除が同時に起きても一致する
- 長期オフラインの端末がリベースしても、削除済みが復活せず、手元にも残らない
- 古いスキーマの端末が新しいフィールドを消さない
- ログの削除と自動整理で tombstone が出ない
- `K` と秘密の設定が書き出しとバックアップに入らない
- 偽サーバーで、通信の切断・409・413・404・`epoch` の変更から回復する
- 領域の削除 → 作り直し → 2 台の合流で全端末が一致し、削除が復活しない
- 枠 2 のシミュレーターの全項目(`docs/sync-security.md`)
- 許可証の否定のテストの全部。押し出しと削除のあと、人の操作なしで作り直せる

## 決定事項

- [x] 置き場所: `bbs-browser` のモノレポ
- [x] 対象: PC 版とスマホ版。Web は含めない
- [x] 同期するもの: テキストだけ。サムネイルと画像の本体は含めない
- [x] サーバー: Cloudflare Workers + Durable Objects(SQLite)
- [x] 通信: HTTP だけのイベント駆動
- [x] 同期は前面の間だけ。スマホの WorkManager とバックグラウンドの処理を使わない
- [x] Cookie・セッションは同期しない
- [x] アプリ証明は使わない
- [x] スマホの暗号ライブラリ: BouncyCastle(`bcprov-jdk18on`)に HChaCha20 を足す
- [x] デプロイ: 手動の `wrangler`。GitHub と連携しない
- [x] Worker: まず `workers.dev` の既定のドメインの検証用だけを作る。本番のドメインは後で決める
- [x] サーバーの URL: 端末の設定に既定値を持ち、利用者は上書きでき、アプリの更新で既定値を書き換えられる。https 以外とリダイレクトを断る
- [x] 公開の順: 検証用 → 先着 100 領域の限定の試験 → 一般公開。「本番のドメイン以外の入口を閉じる」は一般公開の前の条件
- [x] 限定の試験: 招待コードは作らない。枠は環境変数で増やす。Turnstile は限定の試験の段階で必須。PoW は残す。アプリでは試験機能として同意を取る
- [x] 領域の作成: `space_id` に結び付き、サーバーが署名する許可証を要る。サーバーは保存しない。使い始めに 1 度 Turnstile を通し、作り直しは同じ許可証で人の操作なしに行う。QR とコピー用のコードに入れるので 2 台目は Turnstile が要らない
- [x] 受け渡し: ページの移動を端末の窓が止めて受け取る。先は固定の `.invalid`
- [x] 手元のデータが正。同期を切っても、領域が消えても、手元は消えない
- [x] 消された領域の再作成を断らない。端末から作り直せる
- [x] サーバーは保管庫ではなく中継の置き場。満員なら 14 日空いた一番古い領域を押し出す。押し出された端末は確認なしで作り直す
- [x] 台帳: 台帳用の Durable Object
- [x] 作成元: 作成時だけ週替わりの鍵の HMAC を 7 日。平文の IP と User-Agent を保存しない
- [x] 管理 API: Ed25519 の署名。失敗は 404。自動では消さない
- [x] 言語: TypeScript と Kotlin を共通テストで揃える。Rust の共有は採用しない。核の入口を小さく保ち、後から差し替えられるようにする
