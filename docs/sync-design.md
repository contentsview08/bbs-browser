# OBB の PC・スマホ同期 設計

2026-11-07 時点の案。実装はステップ 0(`packages/sync`・`apps/android/.../sync`)まで。

## 概要

PC 版とスマホ版の間で、閲覧履歴・お気に入り・自分の書き込み履歴などを同期する。同期するのはテキストデータだけ。データは端末で E2E 暗号化し、サーバーには暗号文だけを置く。マージはすべて端末で行う。

- 対象は PC 版(Tauri)とスマホ版(Android の Kotlin)。Web(hono-bbs)は含めない
- 掲示板側の協力なしに、専ブラ同士だけで完結させる
- アカウントは作らない。2 台目以降は鍵を受け取って参加する
- 何を同期するかは利用者が選ぶ
- 通信は HTTP だけのイベント駆動。WebSocket の常時接続や短い間隔のポーリングは使わない

## 置き場所

モノレポの `bbs-browser` に置く。共通テストとコネクタの正規化とログの移行が、すでにここにあるため。

| 場所 | 中身 |
| --- | --- |
| `apps/sync-server` | Cloudflare Workers + Durable Objects のサーバー。暗号処理を持たない |
| `packages/sync` | PC 版の暗号・マージ・同期(TypeScript) |
| `apps/android/.../sync` | スマホ版の同じ処理(Kotlin) |
| `packages/conformance/sync-*.json` | PC とスマホが同じ結果を返すための共通テスト |
| `packages/logstore`・`LogDb` | 送信待ちキューと同期の状態の表 |

## 脅威モデル

サーバーが丸ごと漏れても、履歴の中身・見ているスレ・書き込み権限が渡らない。

| 脅威 | 対策 |
| --- | --- |
| サーバーの DB 漏えい | 中身は暗号文。レコード ID は HMAC。認証トークンはハッシュのみ |
| 他人の同期領域へのアクセス | 256bit の認証トークン |
| 暗号文の入れ替え | AEAD の AAD にレコード ID を含める |
| 古い暗号文の再送 | ペイロードの HLC で古いものがマージに負ける |
| 大量の領域作成・データ送信 | 作成ゲート、クォータ、放置削除 |
| 端末の紛失 | 鍵のローテーション。ただし端末に残るデータと権限系の値は漏れたものとして扱う |

### 守らないもの

- サーバーが更新を隠すこと。古い状態を見せ続けられても、端末は検知できない
- メタデータ。通信の時刻と量、IP、暗号文の長さ、レコードの数、どのレコードが何度更新されたか、削除の事実
- 端末が持つ平文のログ。OS とアプリの権限に任せる

暗号文の長さから中身を推測されにくくするため、平文は 256 バイト単位に埋めてから暗号化する。

## 同期するもの

テキストだけを同期する。画像の本体とサムネイルは同期しない。

| レベル | データ | 既定 |
| --- | --- | --- |
| 履歴系 | 閲覧履歴(スレタイ・板名・最終閲覧時刻)・既読位置 | オン |
| 履歴系 | お気に入りのスレ・板(並び順を含む) | オン |
| 履歴系 | 自分の書き込み履歴(サイト・板・スレ・レス番号・時刻) | オン |
| 履歴系 | 上げた画像の履歴(URL・ファイル名・日時) | オン |
| 履歴系 | NG | オン |
| 履歴系 | 許可リストにある設定 | オン |
| 権限系 | 画像の削除キー・管理トークン | オフ |

次は同期しない。

- Cookie・セッション。端末ごとに書き込みの ID が変わることを画面で説明する
- パスワード・API キー・`postDeleteKey`・トリップ入りの名前
- 手元のログ(dat)・読んでいた画面の位置・タブの状態

設定は許可リスト方式にする。新しい項目は既定で同期しない。PC とスマホで持ち方が違う項目(文字の大きさなど)は、対応表にあるものだけを同期する。

## 手元の整理と削除

| 操作 | 同期 |
| --- | --- |
| 履歴から外す・お気に入りを外す | tombstone を送る |
| ログの削除・自動整理 | 同期しない(他の端末の履歴を消さない) |
| クォータ超過で古い履歴をサーバーから外す | tombstone を送るが、手元の履歴は消さない |

## 鍵

最初の端末で 256bit のマスター鍵 `K` を作り、HKDF-SHA256 で用途別の鍵を導出する。`K` はサーバーへ送らない。

| 導出鍵 | info | 用途 |
| --- | --- | --- |
| `auth_token` | `obb-sync/auth` | API の認証 |
| `k_data` | `obb-sync/data` | 履歴系の暗号化 |
| `k_secret` | `obb-sync/secret` | 権限系の暗号化 |
| `k_id` | `obb-sync/record-id` | レコード ID の HMAC |

HKDF の salt は空、長さは 32 バイト。`auth_token` は Bearer では小文字の 16 進で送る。

`space_id = SHA-256(auth_token)` とする(32 バイトそのもののハッシュの小文字の 16 進)。Worker はトークンから `space_id` を計算して Durable Object を選ぶので、トークンのハッシュを別に保存しなくてよい。

`k_secret` は暗号の用途を分けるだけで、端末を分ける効果はない。`K` を持つ端末は権限系も読める。

### 保管

- `K` は OS の鍵保管(Windows の資格情報・Linux の Secret Service・Android Keystore で包む)に置く
- Linux で Secret Service が使えないときは同期を始めず、理由を出す
- `K` と派生鍵は設定の書き出しとバックアップに入れない。どちらも許可リストにないことをテストで確かめる
- 全端末で失うと戻せない。任意でリカバリーコードを書き出せる

### 端末の追加

1. 既存の端末で「端末を追加」を押すと、`K` を含む QR と、同じ内容のコピー用コードを出す
2. スマホは QR を読む。PC にはカメラがないので、コピー用コードを入れる
3. 60 秒で消す。表示中は警告を出し、スマホでは画面の撮影を止める
4. 任意の 6 桁 PIN で、中身を Argon2id の鍵で暗号化できる。写真を撮られたあとの総当たりには強くないので、補助として扱う

### 暗号

- AEAD は XChaCha20-Poly1305。ノンスは毎回ランダム
- ノンスは暗号の処理の中で作り、外から渡す口を作らない。テストは固定のノンスで作った暗号文を開く向きで確かめる
- AAD は `space_id|record_id|kind_tag|schema_version` の UTF-8(区切りは `|`、前後に空白なし)。`space_id` と `record_id` は 64 桁の小文字の 16 進、`kind_tag` は `h` か `s`、`schema_version` は 0 以上の整数の 10 進で、ほかは拒否する。サーバーが振る `version` は暗号化の時点で分からないので入れない
- 埋め草は ISO/IEC 7816-4(`0x80` の後を 0 で埋める)で、次の 256 バイトの倍数まで。必ず 1 バイト以上増える。暗号文は埋め草の長さ + タグ 16 バイトで 16KB まで
- `nonce` と `ciphertext` は JSON では Base64URL(`=` なし)
- 例外の文は決まった符号だけにして、鍵と平文を入れない
- PC は `@noble/ciphers` と `@noble/hashes`
- スマホは BouncyCastle(`bcprov-jdk18on`)。XChaCha がないので HChaCha20 だけ足し、ChaCha20-Poly1305・HKDF・HMAC はライブラリのものを使う。JVM の単体テストで端末と同じコードが動き、純 Java でネイティブのライブラリが増えない。Argon2 もある
- 両者の一致は共通テスト `sync-crypto.json` で確かめる

### 鍵のローテーション

1. 残った端末で `K'` を作る
2. 全レコードを再暗号化し、新しい領域へ送る
3. 古い領域を消す
4. 他の端末は 401 を受けて、再ペアリングを案内する

権限系の値はローテーションでは守れない。画面で、画像の削除キーは漏れたものと考えるよう案内する。

## データモデル

### レコードの ID

```
record_id = HMAC(k_id, "<種類>:<正規化した板 URL>:<スレ>[:<細目>]")
```

`record_id` は小文字の 16 進。各項目の `%` と `:` は `%25`・`%3A` に逃がす(細目に URL が入っても別のレコードと同じ ID にならない)。板のないレコード(設定など)は板を空にする。

板 URL の正規化は `sync-id.json` で PC とスマホを揃える。`5ch.net` と `5ch.io`、http と https、道のある板、末尾の `/`、大文字のホストを同じ規則にする。板名だけでは、別のサイトの同じ名前の板がぶつかる。形はスキームを除いた `ホスト[:ポート]/道/`。http・https 以外は拒否する。

スマホ版にない掲示板(ふたばなど)のレコードも、捨てずに持ち続けて再送する。

### サーバーのレコード

サーバーはレコードごとに最新の 1 件だけを持つ。

```
{
  record_id,
  version,            // 領域の中で単調増加。サーバーが振る
  kind_tag,           // "h" | "s"
  schema_version,
  deleted,            // tombstone か。平文。サーバーの片づけに使う
  nonce, ciphertext,
  updated_at          // サーバーの受信時刻
}
```

`deleted` が平文なのは、中身の見えないサーバーが tombstone を片づけるため。削除の事実はサーバーに見える。端末は平文の `deleted` を見ず、暗号文の中の値を使う(AAD に入っていないので、サーバーが変えられる)。

### ペイロード

暗号化する中身は次の形。知らないフィールドは捨てずに保持する。

```
{ kind, hlc, device_id, deleted?, body?, ...知らないフィールド }
```

- `kind` は種類。`record_id` は片道の HMAC なので、受け取った端末は中身を見ないと種類が分からない
- tombstone は `body` を残さない(最終閲覧時刻だけは max のために残す)
- 数は安全な整数だけ。小数の書き方は言語で違い、キーを並べた JSON が PC とスマホで変わる。順序キーのような小数は文字列で持つ
- 開くときの決まり: 壊れたレコードはそれだけ捨てて理由ごとに数え、ほかを止めない。JSON は深さ 32 まで。復号後の値は種類ごとの決まりで型と長さを検査する。知らない種類は決まりの外なので通して持ち続ける。種類ごとのフィールド名と上限はステップ 3 で実際のデータに合わせて見直す

### マージ

すべてのマージ関数を可換・結合的・冪等にする。

| 種類 | 単位 | 書く端末 | 規則 |
| --- | --- | --- | --- |
| 既読 | スレ×端末、スレごとのリセット | 下記 | 下記 |
| 最終閲覧時刻 | スレ | 全端末 | 時刻は max、ほかは LWW。tombstone をまたいでも max(時刻を除いて勝ち負けを決める。除かないと結合的でなくなる) |
| お気に入り | スレ・板 | 全端末 | LWW。削除は tombstone |
| 並び順 | お気に入りごとの小数の順序キー | 全端末 | LWW。同じ値は ID で並べる。キーは `0.` の後の桁の文字列で、末尾は 0 にしない。文字列の比較がそのまま大小になり、桁が尽きない |
| 自分の書き込み | ランダムな `post_id` | 全端末 | LWW。レス番号が返らない掲示板があるので番号を ID にしない |
| 上げた画像の履歴 | URL | 全端末 | LWW |
| NG・設定 | 要素 | 全端末 | LWW。NG の正規表現は `ng.json` の決まりに従う |
| 削除キー | 画像 | 全端末 | LWW(`k_secret`) |

### HLC

- 形は `壁時計(ms)12 桁の 16 進.カウンター 4 桁の 16 進.device_id` の文字列で、文字列の比較がそのまま順序になる。`device_id` は `[A-Za-z0-9_-]` の 64 文字まで
- 同じ値は `device_id` の辞書順で後の方を勝ちにする。端末を戻すなどで HLC も端末も同じになったら、キーを並べた JSON の順で決める(どの順で受け取っても同じ結果にする)
- 端末に保存する
- 受け取った HLC が今の時刻より 24 時間以上先なら、そのレコードには適用するが、端末の HLC は進めない
- レコードを更新するときは、必ずそのレコードの HLC より大きくする。時計の狂った端末が書いた値も、次の更新で上書きできる。その値が 24 時間以上先なら、更新の値だけが先へ進み、端末の HLC は進めない

時計のずれた端末の書き込みが、実際の順序と逆に勝つことはある。LWW の制約として受け入れる。

### 既読

既読位置を max にすると未読に戻せず、LWW にすると古い端末の位置へ巻き戻る。そのため端末ごとの記録とリセットに分ける。

```
// スレごと・全端末が書く(LWW)
reset: { id, at: HLC, target_res }

// スレ×端末ごと・持ち主だけが書く
dev: {
  base_reset_id,            // この端末が知っている最新のリセット
  pos,                      // base_reset 以降に読んだ最大のレス番号
  steps: [{ at: HLC, pos }] // まだ知らないリセットに備えた記録
}
```

`reset.at` はペイロードの `hlc`、`id` と `target_res` は `body` に置く。`dev` も `body` に置き、記録全体はペイロードの `hlc` で LWW にする。

`steps` は、読むたびに `{ 今の HLC, 読んだ位置 }` を足し、後ろの要素以下の `pos` の前の要素を消す。これで `at` が進むほど `pos` が小さくなる並びになり、任意の時刻より後の最大の位置を先頭側から求められる。最新の 8 件までを持つ。8 件を超えて捨てた分は、知らないリセットの後の読みとして数えられないことがある(既読位置が低く出るだけで、端末間では一致する。テストで確かめた)。

既読位置の計算は次のとおり。

1. `R` = 最新のリセット(なければ id=null・at=0・target_res=0)
2. 各端末の記録について、`base_reset_id` が `R.id` と同じなら `pos` を候補にする
3. 違うなら、`steps` のうち `at > R.at` の `pos` の最大を候補にする
4. 既読位置 = max(`R.target_res`, 候補)

読んだとき、自分の `base_reset_id` が最新のリセットと同じなら `pos` を増やす。違えば `base_reset_id` を更新し、`pos` は「読んだ位置と、そのリセットより後の `steps` の最大」にする。どちらの場合も、そのリセット以前の `steps` を消してから今の読みを足す。

- 前の読みを引き継ぐのは、知らないうちに読んだ分が、同期のあとの読み直しで消えて既読位置が下がらないように
- 今の読みを必ず足すのは、まだ知らない別のリセットより後の読みかもしれないから

未読に戻すときは新しい `reset` を書く。その HLC は、今のリセットと、知っている全端末の記録と `steps` より必ず大きくする。時計が先へ進んだ端末の読みが残っていると、未読に戻せないため。

| シナリオ | 結果 |
| --- | --- |
| PC で 500、スマホで 300 まで読んだ | 500 |
| PC で 500 まで読んだ後、スマホで未読に戻した | 0 |
| スマホで未読に戻した後、知らないオフラインの PC で 350 まで読み、次に開いて 100 まで読んだ | 350 |
| PC で 500 まで読み、スマホで未読に戻した後、PC が同期した | 0 |
| 2 台で同時に別の位置へ未読に戻した | HLC が新しい方 |
| スマホで未読に戻した後、PC が 350 まで読み、同期してから 100 まで読んだ | 350 |
| 時計が 3 日先の PC が 500 まで読み、それを見たスマホで未読に戻した | 0 |

### tombstone と長期オフライン

- サーバーは `deleted` のレコードを 90 日後に消し、消した最大の version を `gc_floor` として返す
- `since < gc_floor` の端末は全件を取り直す(リベース)
- リベースでは、同期済みなのに全件の中にないものを手元から消す。削除済みが手元に残って端末間でずれないため
- 未送信の変更のうち、HLC が 90 日より古いものは捨てる。そのレコードの手元の値も未送信を含むので、全件の値に戻すか、全件になければ消す
- 一度も同期していないもの(`version` が 0。クォータでサーバーから外した手元だけの履歴を含む)は消さない
- 手元の値が全件の値に勝つとき(サーバーが古い値に戻ったときなど)は、送信待ちに入れる
- 消えるものが、全件が空のとき、または 10 件以上かつ同期済みの 20% 以上のときは、自動で消さずに確認を出す。リベースの関数は適用せず、計画を返す
- 同期領域には `epoch` を持たせ、全応答で返す。変わっていたら通番が振り直されたので、リベースする

## API

| メソッド・パス | 認証 | 内容 |
| --- | --- | --- |
| `POST /spaces` | 作成ゲート | 領域の作成 |
| `GET /changes?since=N` | トークン | version N より後の変更(最大 500 件・1MB) |
| `POST /records` | トークン | 一括送信(最大 100 件・1MB) |
| `GET /head` | トークン | 最新の version と `epoch`。ETag と 304 |
| `GET /space` | トークン | 使用量・クォータ |
| `DELETE /space` | トークン | 領域の削除 |

認証は `Authorization: Bearer <auth_token>`。

### 同期の手順

1. `GET /changes` で差分を取り、復号してマージする
2. 送信待ちを暗号化し、`POST /records` で送る。各レコードに `base_version` を付ける
3. `base_version` は、端末が最後に見たその**レコードの** version。新しいレコードは 0
4. サーバーのそのレコードの version が `base_version` より新しければ、その 1 件は 409 になり、応答に今のレコードが入る。端末はマージして再送する
5. 成功したら、新しい version を保存する

### タイミング

| pull のきっかけ | 検知 |
| --- | --- |
| スマホでアプリを開く・復帰する | 前面復帰 |
| PC でウィンドウに戻る | focus・visibilitychange |
| PC で放置後に操作する | 最終操作から 10 分以上空いた最初の操作 |
| オンラインに戻る | 送信待ちを送ってから pull |
| 保険 | 前面にいる間だけ 5 分に 1 回 `GET /head` |

pull は前回から 10 秒以上空ける。

push は次のとおり。

- 変更は送信待ちに溜め、同じレコードは最新の 1 件にまとめる
- 既読はスレを閉じたときに 1 回だけ記録する
- 使用中は、変更があるときだけ 2 分ごとに送る
- お気に入りや書き込みは 10 秒のデバウンスで早めに送る
- 裏に回る・閉じるときに送る。PC は Rust のウィンドウのイベント、スマホは WorkManager で確保する
- 送れなければ次の起動で送る

### エラー

- 1 秒から最大 60 秒の指数バックオフとジッターで再送する。409 はマージして再送し、それ以外の 4xx は再送しない
- 413(クォータ超過)は、古い閲覧履歴と既読から順にサーバーのものを外して再送する。お気に入り・NG・設定は外さない。それでも足りなければ画面で知らせる
- HTTP は 10 秒で打ち切る
- `request_id` で二重の採番を防ぐ
- 画面に「同期中」「同期済み」「送信待ち N 件」「オフライン」を出す

## サーバー

同期領域 1 つに Durable Object(SQLite)を 1 つ割り当てる。通番と楽観ロックは Durable Object の中で完結する。

- トークンから `space_id` を計算して呼ぶ。未作成の領域は空のまま 404 を返す
- 放置削除とレコードの片づけは、各 Durable Object の alarm で行う
- 全体のレート制限と作成数の集計は Cloudflare の Rate Limiting と KV のカウンターで行い、概算でよい
- IP は `space_id` と結び付けて長期に保存しない

### 不正利用対策

アプリ証明は使わない。公開リポジトリのアプリでは強い保証にならず、Play 以外で配る APK は Play Integrity を通らないため。

| 段階 | 対策 |
| --- | --- |
| 作成 | Turnstile(PC もスマホも。アプリの中で動かないときは既存のつなぎのコードの流れを使う)、数秒の PoW、IP ごとの制限(IPv6 は /64) |
| 作成後 | クォータ |
| 運用 | 新規作成だけを止めるサーキットブレーカー |

クォータの初期値は次のとおり。どれも環境変数で変えられるようにする。

| 項目 | 上限 |
| --- | --- |
| 領域の容量 | 10MB |
| レコード数 | 50,000 件 |
| 1 レコード | 16KB |
| 1 リクエスト | 100 件・1MB |
| 頻度 | 20 回/分・2,000 回/日・領域 |
| 放置削除 | 90 日 |

90 日アクセスがなく領域が消えた端末は、404 を受けたら確認を出してから、手元のデータで作り直す。作成ゲートを通るので、裏では作り直さない。

### 費用

1000 人が毎日、スマホを 3 時間、PC を 8 時間使うと仮定する。

| 項目(1 人 1 日) | 回数 |
| --- | --- |
| まとめ送信(スマホ 3 時間の上限) | 90 |
| 裏に回る・閉じるとき | 20 |
| 復帰・フォーカスの pull | 20 |
| PC の保険の確認 | 96 |
| スマホの保険の確認 | 36 |
| 合計 | 約 260 |

月に約 780 万リクエストになる。Workers と Durable Objects の込み分の内外、Durable Objects の実行時間、保存量は、実装の前に最新の料金表で計算し直す。全員が 10MB を使い切ると 10GB になる。テキストだけなので、実際はずっと小さいと見込む。

## 段階

0. **共通の核:** 鍵と暗号、マージ、HLC を TS と Kotlin で作り、`sync-crypto.json`・`sync-merge.json`・`sync-id.json` を両方で通す。スマホの暗号ライブラリを決める。順序をランダムにして同じ変更を重ねても収束するプロパティテストを両方で回す
1. **最小の同期:** サーバー(IP 制限と PoW のみ)、ペアリング、復帰時の pull、手動の同期ボタン。お気に入りと既読だけ
2. **自動同期:** 送信待ちとまとめ送り、きっかけごとの pull、再送、状態の表示、クォータ
3. **対象の拡大:** 閲覧履歴・書き込み履歴・上げた画像の履歴・NG・設定の許可リスト
4. **公開の準備(公開前に必須):** Turnstile、サーキットブレーカー、放置削除
5. **仕上げ:** 権限系、ローテーション、リカバリーコード

WebSocket は、同時利用のリアルタイム性が本当に必要になったときだけ検討する。その場合もデータは HTTP のままで、通知だけを送る。

## 検証

- 同じ変更をランダムな順序・重複ありで適用して、全端末が一致する
- 既読のシナリオ表のすべて
- お気に入りの追加と削除が同時に起きても一致する
- 長期オフラインの端末がリベースしても、削除済みが復活せず、手元にも残らない
- 古いスキーマの端末が新しいフィールドを消さない
- ログの削除と自動整理で tombstone が出ない
- `K` と秘密の設定が書き出しとバックアップに入らない
- 偽サーバーで、通信の切断・409・413・404・`epoch` の変更から回復する
