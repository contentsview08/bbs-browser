# OBB 同期サーバーの安全性とテストの計画

2026-11-07 時点の案。設計は `docs/sync-design.md`。値が食い違うときは、この文書を優先して設計書を直す。

## 前提

- サーバーはインターネットから誰でも届く。アプリを経由しない直接の要求を前提にする
- 公開リポジトリなので、攻撃者はコードと上限の値を全部読める
- サーバーの安全を、クライアントの作りや配布元に頼らない
- 一番の価値は利用者の履歴と書き込みの紐付け。次が権限系の値。サーバーの費用を膨らませる攻撃も主要な脅威と扱う

## 守るものと、破られたときの結果

| 破られるもの | 結果 | 主な防ぎ |
| --- | --- | --- |
| Cloudflare のアカウント・デプロイの権限 | サービス停止、データの削除、メタデータの取得。中身は読めない | 2 段階認証、権限を絞ったトークン |
| アプリの更新の仕組み | **E2E が無効になる**。鍵を送るアプリを配れる | 更新の署名鍵の保管、CI の権限、依存の固定 |
| `K` | その利用者の全データと権限系 | OS の鍵保管、ローテーション |
| `auth_token` だけ | 暗号文の取得と削除、書き込みの妨害。中身は読めない | https のみ、ログに残さない |

E2E でも、サーバーへの攻撃で消せない弱点がこの表の 2 行目にある。リリースの手順は同期の機能と同じ重さで扱う。

## 攻撃と対策

### 入口

| 攻撃 | 対策 |
| --- | --- |
| http でトークンが流れる | 端末は https 以外へ送らない。リダイレクトをたどらない(トークンが別の先へ渡るため)。HSTS |
| `workers.dev` など別の入口を使う | 本番のドメイン以外を無効にする |
| IP の偽装 | `CF-Connecting-IP` だけを使い、`X-Forwarded-For` を信用しない |
| 想定外のメソッド・パス | 決まった組み合わせ以外は 404・405。OPTIONS も応じない |
| ブラウザからの呼び出し | CORS のヘッダーを出さない。Cookie を使わないので CSRF は成立しない |
| 情報の漏れ | 応答は決まったコードだけ。スタックトレースや内部の値を返さない。`Server` 以外の情報を出さない |

### 入力

本文を読む前に検査する。順番は、メソッド → パス → `Content-Length` → レート制限 → 認証 → 本文の読み込み → スキーマ。

| 項目 | 規則 |
| --- | --- |
| 本文 | 1MB まで。`Content-Length` がないか超えていれば 413。読みながらも数える |
| `Content-Type` | `application/json` だけ |
| JSON | 深さと件数を制限し、知らないキーは拒否する |
| `record_id` | 固定長の 16 進か Base64URL だけ |
| `nonce` | 24 バイトちょうど |
| `ciphertext` | 16KB まで。256 バイト単位の長さで AEAD のタグを含むこと |
| `kind_tag`・`deleted`・`schema_version` | 決まった値と型 |
| `since`・`base_version` | 0 以上の安全な整数 |
| `request_id` | 固定長のランダム値 |

SQL はすべてプレースホルダーにする。文字列の連結を CI の検査で止める。

### 認証

- `auth_token` は 256bit。平文を保存しない
- `space_id = SHA-256(auth_token)` なので、比較するトークンがなく、タイミング攻撃の対象がない
- 別の領域を指定する入力がないので、他人の領域を読む経路がない(IDOR が構造的に起きない)
- 領域の作成は、トークンを持つ人だけが自分の `space_id` を作れる。既存の領域に作成を送っても中身を変えない
- 認証の失敗回数を IP ごとに数えて制限する

### 費用と量の攻撃

攻撃者は 1 つの領域とトークンを正しく持てるので、領域ごとの上限だけでは足りない。

| 攻撃 | 対策 |
| --- | --- |
| ランダムなトークンで空の Durable Object を起こす | IP ごとのレート制限を Durable Object の前で行う |
| 正規の領域から連続して要求する | 領域ごとに 20 回/分・2,000 回/日。通常は 1 日 260 回程度 |
| 領域を大量に作る | Turnstile、PoW、IP 制限、全体の作成数のサーキットブレーカー |
| 重い pull を繰り返す | `since=0` は領域ごとに 1 時間 3 回まで。ページの上限 |
| 容量を使い切る | クォータ。作成数 × 10MB を全体の上限として計算する |
| tombstone で埋める | tombstone もレコード数と容量に数える |
| IPv6 で分散する | /64 単位で数える。/48 でも緩く数える |
| 分散した攻撃 | Cloudflare の WAF と DDoS の保護。費用の警告と停止の手順 |
| 費用が膨らむ | 日次の監視と請求の警告。上限を超えたら読み取りだけに切り替える非常スイッチ |

作成の順番は、安いものから先に行う。IP の制限 → PoW の検証 → Turnstile の検証(外部への通信) → 作成。

### PoW と Turnstile

- PoW の問題はサーバーの秘密鍵で署名し、期限(5 分)と `space_id` に結び付ける。使い回しても同じ領域にしか使えない
- 難易度は環境変数で変える。古い端末でも 5 秒程度に収まることを実機で測る
- Turnstile の検証はサーバーで行い、hostname と action を確かめる。期限切れと再利用を拒否する
- 検証サービスの障害時は、新規作成を止める。既存の同期は続ける

### データの悪用

- 暗号化された 10MB の置き場として使われる可能性がある。中身は見られないので、1 レコード 16KB、10MB、放置削除、作成の制限で価値を下げる
- 公開前に利用規約とプライバシーの説明を用意する。違法利用の連絡を受ける窓口と、領域単位で消す手順を決める。法的な扱いは公開前に別途確かめる

### 端末側(悪意のあるサーバーや、乗っ取られた端末)

サーバーの応答も、他の端末からのデータも信用しない。

| 攻撃 | 対策 |
| --- | --- |
| 巨大な応答 | 読み取りの上限。超えたら捨てる |
| ページングの無限ループ | version が進まなければ止める |
| `gc_floor`・`epoch` の繰り返しの変更 | リベースの回数を制限し、画面で知らせる。手元のデータを自動で全消ししない |
| サーバーが全件を空にして見せる | リベースで大量の削除が起きるときは確認を出す。削除の前に手元の一覧を保存する |
| 復号の失敗 | そのレコードだけ捨てて数え、画面に出す。他を止めない |
| 復号後の値が壊れている | スキーマで検査し、型と長さを制限する |
| スレタイなどの文字 | 表示はプレーンな文字として扱う |
| URL | `javascript:` などを拒否し、既存の `safeUrl` と `isAutoLoadable` を通す |
| NG の正規表現 | 既存の NG の検査と同じ制限を通す。同期で来た式で画面が固まらないことをテストする |
| 巨大な NG・設定 | 件数と文字数の上限。範囲の外の設定値を丸める |

### 暗号

- ノンスは暗号の乱数から毎回作る。テストで固定値を使う口を本番に入れない
- 鍵の用途を HKDF の info で分ける。同じ鍵を別の用途に使わない
- AAD の組み立ての形を共通テストで固定する
- 鍵・トークン・平文をログと例外の文に入れない
- 暗号の実装に不具合が見つかったときは、`schema_version` を上げて再暗号化できるようにする
- 外部の専門家の監査を受ける。公開の前か直後に、費用と一緒に判断する

### 運用とサプライチェーン

- Cloudflare のアカウントに 2 段階認証を必須にする。デプロイのトークンは対象の Worker だけに絞る
- サーバーの秘密は `wrangler secret` に入れ、リポジトリに置かない
- `package-lock.json` を固定し、`npm ci` で作る。依存は必要最小限にする
- GitHub Actions はコミットのハッシュで固定し、権限を最小にする
- Dependabot、秘密の検査、CodeQL を入れる。重大なものはリリースを止める
- 本番と別に検証用の環境を持つ。本番のデータを持ち込まない
- ログには `space_id` を残さず、状態コードと種類と量だけにする。IP はレート制限の外に残さない

## テストの計画

| 段階 | 内容 | 自動 | いつ |
| --- | --- | --- | --- |
| 単体 | 入力の検査、認証、クォータ、レート制限、PoW の検証 | CI | 毎回 |
| 統合 | Miniflare で Worker と Durable Object を動かし、全 API を通す | CI | 毎回 |
| 否定のテスト | 下の一覧 | CI | 毎回 |
| ファズ | 本文・ヘッダー・パスをランダムに崩して、500 が出ないこと | CI(短時間)・夜間(長時間) | 毎回・毎晩 |
| プロパティ | 収束、順序、重複、リベース | CI | 毎回 |
| 共通テスト | TS と Kotlin の暗号とマージの一致 | CI | 毎回 |
| 障害注入 | 切断、409、413、404、`epoch` の変更、途中の 500 | CI | 毎回 |
| 負荷 | 検証用の環境で、想定の 10 倍の要求と限界値 | 手動 | 公開前・大きな変更時 |
| 費用 | 負荷の結果から月額を計算する | 手動 | 公開前 |
| 実機 | PC(Windows・Linux)とスマホの実機で、機内モードの復帰と 2 台の同時利用 | 手動 | 各段階 |
| 依存と静的解析 | `npm audit`、CodeQL、秘密の検査 | CI | 毎回 |
| 侵入テスト | 検証用の環境で、下の一覧を外から試す | 手動 | 公開前 |

### 否定のテストの一覧

- トークンなし・短い・形の違う・別の領域のトークン
- 本文が 1MB を超える、`Content-Length` が嘘、途中で切れる、圧縮爆弾
- JSON が壊れている・深い・キーが重複・巨大な数値・型違い
- `record_id`・`nonce` の長さ違いと SQL の断片
- 101 件の送信、16KB を超えるレコード、クォータちょうどと 1 バイト超え
- `since` の負数・小数・巨大な値・文字列
- 同じ `request_id` の再送(通番が増えないこと)
- 同時の書き込み(通番の重複と取りこぼしがないこと)
- 期限切れ・他の領域の・改ざんした PoW
- 再利用した Turnstile トークン。検証サービスの障害
- `workers.dev` と http への要求
- 作成済みの領域への作成(中身が変わらないこと)
- 応答とログにトークンと IP が出ないこと

### 悪意のあるサーバーのテスト(端末側)

偽のサーバーで、次を返して端末が壊れないことを確かめる。

- 巨大な応答、進まない version、壊れた暗号文、別の領域の暗号文
- 古い暗号文の再送、レコードの入れ替え
- `epoch` と `gc_floor` の連続の変更、全件を空にした応答
- 別のドメインへのリダイレクト(トークンを渡さないこと)
- 復号後に長すぎるスレタイ・`javascript:` の URL・極端な正規表現

## 公開の前の条件

次がすべて終わるまで、一般に公開しない。

- [ ] 上の自動テストがすべて通り、CI で止まる
- [ ] 本番のドメイン以外の入口を閉じた
- [ ] レート制限とクォータとサーキットブレーカーを、検証用の環境で実際に発動させた
- [ ] 負荷と月額の計算を、最新の料金表で確かめた
- [ ] 請求の警告と非常スイッチを本番で確かめた
- [ ] 侵入テストの結果を直した
- [ ] 利用規約、プライバシーの説明、脆弱性の連絡先(`SECURITY.md`)を用意した
- [ ] 下の手順書を書いた
- [ ] 外部の監査を受けるかを決めた

## 事故の手順(公開前に詳しく書く)

| 事故 | 最初の動き |
| --- | --- |
| 費用や要求の急増 | 非常スイッチで新規作成を止める。必要なら読み取りだけにする |
| デプロイのトークンの漏えい | 無効にして作り直す。デプロイの履歴を確かめる |
| サーバーの DB の漏えい | 中身は暗号文でも、メタデータの漏えいとして利用者に知らせる |
| 暗号の不具合 | 新しい版を出す。ローテーションを案内する |
| 更新の署名鍵の漏えい | 配布を止める。新しい鍵は既存のアプリが受け付けないので、手での入れ直しを案内する |
| 悪いデプロイ | 前の版へ戻す。Durable Object のスキーマの変更は戻せる形で行う |
